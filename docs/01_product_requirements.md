# プロダクト要求仕様書

## 1. 背景・目的
- 自社サービスとして新規リリースする「おみくじAPI」のインフラを構築する。
- アプリケーション開発チームがAPI自体の開発は完了済み。人気サービスになることが見込まれるため、高可用性・スケーラビリティを備えたインフラが求められている。

## 2. 対象ユーザー・ステークホルダー
- エンドユーザー: おみくじAPIを利用する外部/社内クライアント
- アプリケーション開発チーム: API本体の開発・提供元
- インフラチーム(本プロジェクト担当): ELB/Auto Scalingによるインフラ構築・運用

## 3. ビジネス要求
- おみくじAPIサーバをEC2(Amazon Linux 2023)上に構築し、ELB配下で複数台稼働させる。
- APIサーバの初期構築は、別途提供されるシェルスクリプトをEC2のユーザデータとして実行することで行う。
- 複数のアベイラビリティゾーンに分散配置し、単一AZ障害時も可用性を維持する。
- CPU使用率に応じてAPIサーバをAuto Scalingで自動増減する。

## 4. 非機能要求
- 可用性:
  - ロードバランサー(ALB)配下に複数AZのAPIサーバを配置し、単一AZ障害時もサービス継続可能とする。
  - Auto Scalingにより通常時2台、CPU使用率70%超過時に最大4台まで自動拡張する。
- セキュリティ: 本基盤の [docs/05_development_guidelines.md](./05_development_guidelines.md) の必須ルール(checkov/Trivy/機密情報管理/バージョン方針)を前提とする。加えて以下を満たすこと。
  - ロードバランサーはインターネットからのHTTP(80番ポート)通信のみ許可する。
  - APIサーバはロードバランサーからの80番ポート通信のみ許可し、インターネットからの直接アクセスは拒否する。
  - APIサーバはソフトウェアインストールのため、インターネットへのアウトバウンド通信(NAT経由)は許可する。
- コスト:
  - EC2インスタンスタイプは無料利用枠対象の `t2.micro` を使用する。
  - NAT Gatewayはコスト最適化のため、AZごとではなく単一構成(1つ)とする(可用性よりコストを優先するdev環境向けの判断)。
- 運用:
  - APIサーバへのSSH(22番ポート)による直接ログインは許可しない方針とする(要件4に基づき、80番ポート以外の受信は許可しない)。運用時のログイン手段が必要な場合はSSM Session Manager等、インバウンドポート開放を伴わない方式を別途検討する。

## 5. スコープ外
- APIアプリケーション自体の実装(開発チームが別途提供するユーザデータスクリプトに準拠)。
- HTTPS化(ACM証明書・独自ドメイン)は本スプリントのスコープ外(要件はHTTP/80番ポートのみ)。
- マルチリージョン構成、DR(災害復旧)設計。

## 6. 成功指標(KPI)
- ALB経由でおみくじAPIに正常アクセスできること。
- APIサーバを1台停止させてもALB経由でサービス継続できること(複数AZ・複数台構成の検証)。
- 負荷試験等でCPU使用率が70%を超えた際に、Auto ScalingでEC2インスタンスが自動増加すること(最大4台まで)。
- checkov/tflintのCritical/High指摘がゼロであること。
